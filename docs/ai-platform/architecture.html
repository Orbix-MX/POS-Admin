Lo que no cambia

  • La IA no escribe en la base de datos. Draft efímero → validación → confirmación humana → ProductsService.create(). Un único camino de escritura.
  • Los módulos de negocio no conocen al proveedor. Es la razón de existir de esta arquitectura, y se hace cumplir con una regla de ESLint en CI.
  • llama.cpp en producción, Ollama en desarrollo, con gramáticas GBNF que garantizan JSON válido por construcción.
  • El conjunto de evaluación en español mexicano es obligatorio y decide el modelo. Sin él, cambiar de modelo es a ciegas.
  • El consumo vive en PostgreSQL, con tenant, feature, modelo, tokens, latencia, costo estimado y resultado.
El riesgo que la simplificación concentra

Con un solo proveedor y sin fallback, el servidor de inferencia es un punto único de fallo para la feature. Esto es aceptable — y deliberado — porque el principio 04 lo cubre: ninguna operación de negocio depende de la IA. Si el modelo cae, el alta manual de productos funciona exactamente igual. Lo que se pierde es una aceleración, no una capacidad. A cambio se evita construir hoy toda la maquinaria de resiliencia multiproveedor, que es la parte más cara y más difícil de probar.

01 — Principios rectoresOcho reglas que no se negocian

Cuando una decisión posterior contradiga una de estas, gana la regla.

Regla 01 La IA propone, Orbix dispone

Ningún camino de código permite que una respuesta del modelo llegue a la base de datos sin pasar por un servicio de dominio y una confirmación humana.

Regla 02 · la central El negocio no conoce al proveedor

Los módulos de negocio no conocen OpenAI, Anthropic, llama.cpp, Ollama, modelos concretos, API keys, tokens ni costos. Solo conocen la capacidad de IA que necesitan. Se hace cumplir con ESLint, no con buenas intenciones.

Regla 03 La IA nunca inventa identificadores

El modelo devuelve nombres y textos. Los uuid, tenantId, categoryId y createdById los pone el servidor, siempre.

Regla 04 Ninguna operación depende de la IA

Todo lo que el asistente acelera se puede hacer a mano. Si la IA cae, el POS y el alta de productos siguen funcionando idénticos. Es lo que hace aceptable no tener fallback.

Regla 05 Nada consume sin tope

Límite mensual por tenant y límite de ráfaga por usuario, desde la primera versión. El sistema rechaza la invocación antes de llegar al modelo.

Regla 06 El cliente nunca ve credenciales

Flutter conoce featureKey y recibe drafts. No existe endpoint que devuelva configuración de proveedor al dispositivo. Vale hoy con el local y valdrá igual cuando haya claves de pago.

Regla 07 Todo dato de IA lleva tenantId

Igual que el resto de Orbix, desde TenantContextService.requireTenantId(). Incluye contadores y cualquier clave de caché que llegue a existir.

Regla 08 Degradación explícita, nunca silenciosa

Si el gateway reparó un JSON o entregó un draft parcial, lo dice en la respuesta y en el evento de consumo. Un fallo silencioso es un fallo que nadie corrige.

Decisión D-01 · vigente

¿Secuencia explícita o pipeline configurable de middlewares?

  • Secuencia explícita — se lee de arriba abajo, se depura con un breakpoint, el orden es evidente en el código.
  • Pipeline de middlewares — cada feature compondría sus pasos. A cambio: indirección, orden implícito, peores stack traces.

Secuencia explícita. Con una feature y un proveedor, el pipeline configurable resuelve un problema inexistente. Regla de reevaluación: extraerlo cuando más de tres features necesiten órdenes de pasos distintos.

Detalle con consecuencias

El paso 8 no debe bloquear la respuesta, pero tampoco puede perderse. Patrón: escribir el evento en la misma transacción que actualiza el contador del tenant, después de haber enviado la respuesta, con buffer en memoria y volcado por lote cada 2 s o 50 eventos. Perder telemetría es tolerable; perder el decremento del contador convierte el límite en decorativo.

Decisión D-16 · nueva

Con un solo proveedor, ¿hace falta el puerto?

  • Sin puerto — ProductAIService llamaría a un cliente HTTP de llama.cpp. Menos código hoy. Cuando llegue Anthropic, habría que refactorizar todos los consumidores.
  • Con puerto — una interfaz y un registro. Cuesta ~60 líneas y un archivo.

Con puerto, y es innegociable — es la razón de ser de todo este documento. Y hay una prueba concreta de que no es teatro arquitectónico: la v1 tiene dos implementaciones del puerto desde la Fase 1, OpenAICompatibleProvider y MockProvider. Una abstracción con dos implementadores reales ya está validada; con uno solo, es una suposición.

El puerto

interface AIProvider {

05 — Structured outputJSON válido no es JSON correcto

Hay dos problemas distintos que se confunden todo el tiempo. El primero es sintáctico: que el modelo emita JSON que parsea y cumple el schema. El segundo es semántico: que los valores existan en el tenant y respeten las reglas del negocio. El primero se resuelve con tecnología; el segundo, solo con código de dominio.

Garantía sintáctica en la v1

Orbix usa decodificación restringida por gramática: la definición Zod se convierte a JSON Schema y de ahí a una gramática GBNF que se envía a llama-server. El modelo no puede emitir un token que rompa el schema. Es una garantía del decodificador, no una esperanza sobre el prompt.

Ventaja del local que conviene tener presente

En structured output, el modelo local tiene una garantía más fuerte que cualquier proveedor cloud, porque controlamos el decodificador. OpenAI y Anthropic ofrecen garantías altas, pero no del 100 % y no auditables. Es un argumento técnico real — independiente del costo — a favor de mantener el local para tareas de extracción y estructuración.

Decisión D-02 · vigente

¿Zod o class-validator como fuente de verdad de los schemas de IA?

  • class-validator — ya está en Orbix para DTOs HTTP, pero no tiene camino limpio a JSON Schema, y sin JSON Schema no hay gramática.
  • Zod — una definición genera el validador, el JSON Schema, la gramática GBNF y el tipo TypeScript del draft.

Zod, confinado a src/ai/ y a los *.schema.ts de los servicios de IA. Los DTOs HTTP siguen con class-validator sin cambios — son fronteras distintas y conviven sin conflicto.

Las dos capas de validación

Capa 1 · técnica Schema Zod

Tipos, campos requeridos, enums cerrados, rangos numéricos, longitudes. Se ejecuta sobre la salida cruda del modelo.

Si falla: un reintento con el error inyectado, presupuesto de tokens acotado.

Capa 2 · dominio Reconciliador

Resuelve nombres a entidades reales del tenant: categoría, unidad de medida, TaxCode, unicidad de SKU. Vive en modules/, no en ai/.

Si falla: el campo se marca unresolved y sube a la UI como decisión del usuario.

Política de reparación

  • Máximo un reintento. Un segundo rara vez cambia el resultado y duplica la latencia — que en CPU local es el recurso escaso.
  • El reintento incluye el error de validación como texto ("price debe ser number, recibí '22 pesos'"), no el schema completo otra vez.
  • Nunca un error 500 por schema inválido. Se devuelve el draft parcial con fieldsFailed: ['taxCode']. Un draft con seis campos buenos es útil; un error no.
  • Reparación exitosa → evento con estado SCHEMA_REPAIRED. Es la señal temprana de que el modelo o el prompt se están degradando.
Regla que elimina una clase entera de errores

El schema del draft no contiene ningún campo de tipo id. No hay categoryId, hay categoryName. El modelo no puede alucinar un UUID inexistente si la gramática no le permite emitir UUIDs. El mapeo a identificadores es responsabilidad exclusiva del reconciliador, con una consulta real a la base de datos del tenant.

06 — Prompt managementLos prompts son código

Decisión D-03 · vigente

¿Dónde viven los prompts?

  • Hardcodeados en el servicio — descartado. Imposible versionar o comparar entre versiones.
  • Archivos versionados en git (templates/<feature>/<name>.v1.md con frontmatter YAML), cargados al arranque en un registro inmutable.
  • Tabla en Postgres, editable en caliente. Servicio externo tipo Langfuse.

Archivos en git. Un prompt cambia el comportamiento del producto: merece revisión, CI, git blame y rollback junto al deploy. El PromptRegistry expone resolve(featureKey, { locale }), así que añadir una fuente en base de datos más adelante es implementar un segundo PromptSource, no rediseñar.

El orden no es estético. llama-server reutiliza el KV cache del prefijo común entre peticiones: con el bloque estable primero, el prefill de ~1.5 K tokens deja de pagarse en cada invocación del mismo tenant. En CPU eso es la diferencia entre 20 s y 12 s. Es la optimización de latencia con mejor relación esfuerzo-resultado de todo el diseño, y solo requiere ordenar bien el prompt.

Versionado

  • Inmutable. Una versión publicada no se edita; se crea v2. Así una regresión se localiza por diferencia entre versiones.
  • La versión activa está en ai-feature.binding.ts, junto al modelo. Cambiar de v1 a v2 es una línea de configuración.
  • El consumo registra promptVersion. Sin eso no se puede atribuir un cambio en la tasa de aceptación a un cambio de prompt.
  • Sin variantes por modelo en v1. Se introducen solo si las evaluaciones demuestran que un modelo concreto las necesita.
Diferido

A/B testing de prompts, prompts editables en caliente y overrides por tenant. El diseño los admite — el registro ya resuelve por clave y versión — pero con pocos tenants piloto no hay potencia estadística para concluir nada de un experimento.

Decisión D-04 · vigente

¿Se persiste el draft?

No. Efímero. El draft viaja en la respuesta HTTP y vive en la memoria del cliente. Persistirlo añadiría una tabla, un ciclo de vida y un job de limpieza sin beneficio demostrado. Pero el aiRequestId sí viaja de ida y vuelta: el cliente lo devuelve al crear el producto, y eso permite registrar el outcome sin persistir nada. Se replanteará cuando exista conversación multi-turno o alta por lotes.

La métrica que decide el futuro del proyecto

outcome ∈ ACCEPTED · EDITED · DISCARDED, más qué campos tocó el usuario. Los tokens dicen cuánto costó; el outcome dice si sirvió. Es lo que permite responder "¿el modelo local es suficientemente bueno?" con un número en vez de una opinión — y es el criterio que decidirá si algún día vale la pena un proveedor cloud o una GPU. Cuesta un campo y un identificador de ida y vuelta. Debe estar en la v1.

Casos que el prompt debe manejar desde el día uno

  • Jerga real de mostrador mexicano: "coca de 600", "cagua", "torta de jamón", "sabritas grandes". Un modelo entrenado mayoritariamente en inglés falla aquí, y este es el criterio de selección de modelo más importante — más que cualquier benchmark académico.
  • Ambigüedad de precio: "me cuesta 15 y la doy en 22" frente a "la vendo en 22 con todo e impuestos". El segundo caso implica precio con IVA incluido — el modelo debe marcarlo, no adivinarlo.
  • Información faltante: si no se mencionó el costo, el campo va vacío. Nunca inventar un costo — contamina márgenes y reportes financieros en silencio.
  • Varios productos a la vez: la v1 rechaza explícitamente y pide uno por uno.
  • Entrada sin sentido o maliciosa: devuelve draft vacío con motivo, no una excepción.

La invariante estructural

ProductAIService no inyecta PrismaService para escritura. La creación ocurre en una petición HTTP posterior e independiente, disparada por una acción explícita del usuario, contra el endpoint normal de productos, con el DTO normal y las validaciones normales, y con createdById = el usuario real. Por qué esto también es la mejor defensa de seguridad

Como la IA no tiene tool calling contra la base de datos, un ataque de prompt injection escondido en el nombre de un producto no puede crear, modificar ni borrar nada. Lo peor que consigue es proponer un borrador raro que un humano rechaza. Esa contención es arquitectónica: no depende de que el prompt esté bien escrito.

Decisión D-05 · vigente, simplificada

¿Qué runtime de inferencia local?

  • Ollama — DX excelente, gestión de modelos integrada, API compatible con OpenAI. Es un envoltorio sobre llama.cpp: hereda sus límites y añade su propio retraso de versión, gestión opaca de carga y descarga (keep_alive) y menos control del batching bajo concurrencia.
  • llama.cpp / llama-server — el motor real. GGUF con cuantización agresiva, rendimiento aceptable en CPU, gramáticas GBNF, slots paralelos, métricas Prometheus nativas, control fino de contexto y KV cache. Coste: elegir flags y operar el binario.
  • vLLM — el mejor rendimiento agregado que existe, pero diseñado para GPU. Sin VRAM es inviable. diferido hasta que exista una GPU.

llama-server en producción, Ollama en las máquinas de desarrollo. Y no son dos integraciones: ambos exponen la API de OpenAI, así que Orbix escribe OpenAICompatibleProvider una sola vez y el runtime es una baseUrl en configuración. La razón decisiva de llama.cpp en producción son las gramáticas GBNF: convierten "esperemos que el JSON salga bien" en una garantía del decodificador.

Decisión D-06 · cerrada 16 ago 2026, con evidencia — re-evaluable si cambia el runtime

¿Qué modelo local?

  • Qwen3-4B-Instruct Q4_K_M ≈ 2.6 GB — candidato inicial por licencia y tamaño. Descartado en la práctica: vía Ollama es un modelo "thinking" que gasta el presupuesto de salida completo razonando (verificado con 300 y con 1500 tokens, 0% de JSON emitido) y think:false no lo suprimió en esta versión de Ollama. Ver el informe de benchmark de Fase 2.
  • Llama-3.2-3B-Instruct Q4_K_M ≈ 2.0 GB — sin modo "thinking", responde directo. Evaluado contra las 30 entradas: 100% JSON válido, 0/30 costos inventados. Licencia Llama Community (aceptada por ahora — ver riesgo).
  • Gemma4:26B — descartado sin evaluar a fondo: timeout a 120 s en la primera petición, incluso con GPU disponible. Confirma la aritmética de §10.
  • Qwen3-8B, Ministral-8B, Gemma-3-4B-it, Phi-4-mini — sin evaluar todavía.

Llama-3.2-3B-Instruct, hoy. Decisión tomada con datos reales (30/30 casos, ver informe de benchmark), no con lectura de benchmarks generales — cumple el criterio de la Fase 2. Sigue siendo re-evaluable: Qwen3-4B no está descartado como modelo, solo bloqueado con este runtime — vale la pena repetirlo contra llama-server antes de cerrarlo del todo. El modelo se cambia por configuración (config/ai-model.catalog.ts): ningún cambio en ProductAIService cuando eso pase.

Estado actual: sin servidor de inferencia propio todavía

Decisión explícita de no aprovisionar el VPS de inferencia por ahora — se sirve desde Ollama en la máquina de desarrollo, no desde llama-server en infraestructura propia. Es una etapa deliberada, no un descuido: nada en v1 depende de que el servidor de inferencia exista todavía (ai.echo sigue en mock, ninguna feature de negocio está construida). El riesgo de abajo — no compartir host con la API — sigue vigente para cuando se aprovisione, y aplica igual de fuerte entonces.

Riesgo operativo a evitar cuando exista un servidor de producción

No ejecutar el modelo en el mismo host que la API de producción. La inferencia en CPU satura todos los núcleos durante decenas de segundos; con Postgres y NestJS en la misma máquina, cada generación de un draft degrada la latencia del POS de todos los tenants. Un VPS de inferencia pequeño y separado cuesta poco y elimina el peor modo de fallo del sistema. Si por presupuesto hay que compartir host en el piloto, aislar con cpuset/cgroups y limitar a un solo slot.

La latencia es el riesgo número uno de la v1

Un draft en 15–25 s no es una espera trivial: es tiempo en el que el usuario podría haber llenado el formulario a mano. La Fase 2 debe medirlo antes de construir el asistente, no después. Tres salidas si el número es malo, en orden de preferencia: (1) ordenar el prompt para maximizar reutilización del KV cache — ya está en el diseño; (2) reducir el modelo o el maxOutputTokens, midiendo el impacto en las evaluaciones; (3) reconsiderar el alcance de la feature. Un proveedor cloud o una GPU son respuestas válidas, pero ambas están explícitamente fuera del alcance de la v1 y requieren una decisión aparte, con los datos de la Fase 2 sobre la mesa.

Reglas de dimensionamiento

  • Pesos: parámetros × bits ÷ 8. Un 4 B en Q4_K_M ocupa ≈ 2.6 GB.
  • KV cache: ≈ 2 × capas × cabezas_kv × dim_cabeza × contexto × slots × 2 bytes.
  • Margen: ~15 % de sobrecarga sobre pesos + KV.
  • Escalado: primero subir slots, luego vCPU, y solo después plantear GPU — con la métrica que lo justifique.
Fuera del alcance de la v1

GPU, vLLM, servidor de embeddings, pgvector, múltiples hosts de inferencia. Ninguno es necesario para el Product Assistant, y cada uno añade una pieza que operar. La sección Fase 5+ define qué métrica dispara cada uno.

Decisión D-17 · nueva

¿Binding en código o tabla de routing en la base de datos?

  • Tabla — cambiar de modelo sin deploy, overrides por tenant, A/B testing. Cuesta dos migraciones, un repositorio, un resolutor de precedencia y una caché.
  • Constante en código + overrides por entorno — cambiar de modelo es una variable de entorno y un reinicio del proceso. Cero migraciones.

Constante en código. Con una feature y un proveedor, la tabla de routing sería infraestructura para un grado de libertad que nadie va a usar. El requisito real es "cambiar el modelo sin modificar ProductAIService", y una variable de entorno lo cumple. La tabla llega en la Fase 4, junto con el segundo proveedor, que es cuando la precedencia empieza a significar algo.

Decisión D-07 · vigente, reformulada

¿El plan comercial determina el proveedor de IA?

  • Escalera por plan (STARTER → local, PLUS → cloud…) — intuitiva de vender, pero acopla la promesa comercial a la implementación técnica. Si mañana el local resulta mejor, la escalera se vuelve absurda: "pagué el plan caro y me dan lo lento".
  • El proveedor no es atributo del plan — el plan define límites y qué features están habilitadas; nada más.

El proveedor no forma parte del plan. En la v1 la cuestión es doblemente sencilla: los cinco planes usan IA local, porque es el único proveedor que existe. El plan solo modula cuánto se puede usar y qué features están habilitadas. Esta decisión puede evolucionar: si en el futuro un proveedor cloud atiende ciertas features, la elección seguirá siendo de Orbix por clase de tarea, no un atributo vendido en la lista de precios.

¿Qué pasa cuando el proveedor local no responde?

Error tipado, observable y explicado — sin intentar nada más. Es aceptable porque el principio 04 lo cubre: el alta manual de productos funciona idéntica sin la IA. ¿Encolar las peticiones de IA hechas sin conexión?

El alta de producto es una tarea sincrónica: un borrador que llega tres horas después es ruido, porque el usuario ya creó el producto a mano — y entonces hay dos registros y nadie sabe cuál vale. El conjunto de evaluación · entregable obligatorio de la Fase 0

30–50 entradas reales en español mexicano, con la jerga de mostrador que aparecerá de verdad, cada una con su ProductDraft esperado revisado por alguien de negocio. Se ejecuta en CI contra el modelo activo y mide cinco cosas:

  • Schema válido al primer intento — porcentaje
  • Categoría correcta tras la reconciliación
  • Unidad correcta tras la reconciliación
  • Precio y costo — error absoluto, y tasa de "inventó un costo que no estaba en la entrada"
  • Coincidencia con el draft esperado — campo a campo

Es lo que convierte la elección de modelo en una decisión con evidencia en lugar de una lectura de benchmarks generales, que miden otra cosa y en otro idioma. Y es lo que hará que añadir un proveedor en la Fase 4 sea seguro: se compara contra el mismo conjunto. Sin esto, cambiar de modelo es a ciegas.

CierreQué NO debemos construir todavía

Esta sección es normativa. Cada elemento resuelve un problema que Orbix todavía no tiene, y construirlo ahora costaría mantenimiento durante meses antes de dar valor.

No construir Múltiples proveedores

El puerto queda listo. AnthropicProvider y OpenAIProvider no se escriben. La abstracción ya está validada por tener local + mock.

No construir Fallback automático

Sin un segundo proveedor no hay destino. Error tipado y observable en su lugar.

No construir Routing avanzado

Ni tablas, ni precedencia, ni candidatos ordenados, ni filtros por clase de tarea. Una constante feature → modelo.

No construir Créditos, facturación y overage

Se registra el consumo y se aplican límites por invocaciones. Cobrar es una decisión con tres meses de datos por delante.

No construir BYOK y gestión de secretos

El servidor local no lleva API key. Llega con el primer proveedor de pago, en la misma entrega que el kill switch.

No construir Embeddings y pgvector

El Product Assistant no los necesita. El contexto del tenant son decenas de elementos y cabe en el prompt.

No construir Streaming

Transmitir JSON estructurado token a token es frágil, y la respuesta útil es el objeto completo validado.

No construir Redis, colas y workers

Nada en las fases 1–3 lo exige con una sola instancia. Las interfaces de límite quedan preparadas; la infraestructura, no.

No construir Kubernetes y autoescalado

Se escala subiendo slots y vCPU. Introducir un orquestador por la IA sería resolver un problema organizativo con infraestructura.

No construir Agentes con tool calling contra la BD

La tentación más grande y el mayor riesgo. Rompe el principio 01 y abre toda la superficie de prompt injection que hoy está cerrada por construcción.

No construir Panel de prompts y A/B testing

Los prompts viven en git y se despliegan con el código. Con pocos tenants piloto no hay potencia estadística para un experimento.

No construir Visión, OCR y multi-turno

Extraer datos de una factura escaneada es otra clase de problema. La memoria conversacional implica persistencia, ventana y coste creciente.

No construir Device AI

Contrato reservado en el puerto. Exige una feature de alto volumen, tolerante y offline; el asistente no cumple ninguna de las tres.

No construir n8n en la ruta de inferencia

Nunca. Como consumidor de eventos de dominio, más adelante y fuera del camino crítico.

No construir Asistentes en otros verticales

Restaurante, taller, gimnasio y servicios esperan. Una feature bien resuelta en retail enseña más sobre la plataforma que cuatro a medias.

No construir Gateway externo (LiteLLM, OpenRouter)

Resuelven la parte fácil y no la difícil. Se reevalúa si Orbix superara los cinco proveedores simultáneos.

El criterio, en una frase

La v1 debe caber en la cabeza de una persona: un puerto, un adaptador, un prompt, un schema, una feature y un límite. Todo lo demás son extensiones del mismo diseño, añadidas cuando un número — no una intuición — las pida.
